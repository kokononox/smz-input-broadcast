# طرح سامانهٔ پخش ورودی SMZ

## هدف نسخهٔ آزمایشی

یک Windows app روی سیستم مادر، ورودی عادی موس و صفحه‌کلید را هنگام پخشِ صریح جمع‌آوری و به یک کلاینت SMZ بفرستد. رایانه‌ها در اختیار کاربر و در یک اتاق هستند. نسخهٔ اول برای سنجش تأخیر و کیفیت است.

## معماری

`موس/صفحه‌کلید مادر → برنامهٔ بومی Windows → USB CDC/COM → Pico مادر → UART1 روی GP8/GP9 → Pico کلاینت → مسیر فعلی Pico/Pro Micro → رایانهٔ کلاینت`

Pico به‌تنهایی رویدادهای صفحه‌کلید و موسِ متصل به Windows را نمی‌بیند؛ برنامهٔ Windows باید رویدادها را دریافت و از COM به Pico مادر بدهد. برنامهٔ دریافت‌کنندهٔ Windows باید بومی باشد؛ Python در مسیر بلادرنگ به‌کار نمی‌رود. تقسیم کار کلاینت طبق گفتهٔ کاربر: تایپ در Pico و حرکت موس در Arduino Pro Micro است. برای کلیک و اسکرول باید از مسیر فعلی همان کلاینت استفاده شود.

## جریان واقعی ساخت فریمور

سه فایل نمونه‌ای که کاربر فرستاد متعلق به نسخهٔ قدیمی‌تر Classroom Studio با سنسور نوری‌اند و فقط برای فهمیدن فرمت و روند استفاده می‌شوند؛ فایل‌های `.amsj` و `.uf2` در این مخزن کپی نمی‌شوند.

در سورس فعلی SMZ، Classroom Studio پروژه را به `program.abp` کامپایل می‌کند و سپس محتوای آن را در اسلات ثابت یک UF2 پایه قرار می‌دهد. این کار را `NativeUf2Exporter.cs` با `abvm.py` و `abvm_uf2.py` انجام می‌دهد؛ فایل خروجی برای برنامه‌ریزی Pico ساخته می‌شود. ابزار Python در اینجا ابزار ساخت/خروجی‌گیری است، نه برنامهٔ بلادرنگی که رویدادهای موس و صفحه‌کلید را بگیرد. هسته و آداپتر Pico در مسیر native C ساخته می‌شوند. [NativeUf2Exporter.cs](https://github.com/kokononox/smz/blob/7651e5a1f81e19885ae15bbbcce9be8c4ecbd8a3/ams-shell/src/Ams.UI/Services/NativeUf2Exporter.cs) · [abvm_uf2.py](https://github.com/kokononox/smz/blob/7651e5a1f81e19885ae15bbbcce9be8c4ecbd8a3/tools/abvm_uf2.py) · [ساخت فریمور Pico](https://github.com/kokononox/smz/blob/7651e5a1f81e19885ae15bbbcce9be8c4ecbd8a3/firmware/abvm/pico/README.md)

پس برای اضافه‌شدن قابلیت جدید، دو مرحله از هم جدا هستند:

1. تغییر و ساخت runtime بومی Pico؛ سپس تولید دوبارهٔ مجموعهٔ UF2های پایهٔ ۳۰ هویت.
2. Classroom Studio طبق روال خودش پروژهٔ `.amsj` را کامپایل و در UF2 پایهٔ جدید قرار می‌دهد.

فایل‌های ارسالی کاربر شواهد خوبی برای فهم رابطهٔ فایل پایه و خروجی برنامه هستند، اما چون از نسخهٔ قدیمی‌اند، مبنای پیاده‌سازی کد جدید نیستند. فقط سورس runtime فعلی و مسیر ساخت آن مبنا خواهد بود.

## پایه‌ها و سیم‌کشی

- دکمه‌های فیزیکی فعلی روی **GP3، GP4 و GND** هستند؛ برای لینک جدید استفاده نمی‌شوند.
- **GP16/GP17** برای UART0 فعلی Pico به Pro Micro استفاده می‌شوند و آزاد نیستند.
- کاربر تأیید کرده **GP8/GP9 روی Pico مادر و کلاینت آزادند**؛ UART1 گزینهٔ لینک بردبه‌برد است. اتصال نهایی باید TX↔RX و GND مشترک را رعایت کند.
- طول کابل بین دو Pico بیش از ۰٫۵ و کمتر از ۳ متر است.
- نقشهٔ سیم‌کشی قدیمی GP2/GP3 را برای دکمه‌ها نشان می‌دهد، اما وضعیت واقعی اعلام‌شدهٔ کاربر (GP3/GP4) مبناست.

## ترتیب پیاده‌سازی

1. **لینک native C بین دو Pico:** heartbeat، شمارهٔ توالی و ACK روی UART1؛ ابتدا هیچ رویداد HID اجرا نشود. این آزمون با فریمور ساخته‌شده انجام می‌شود، نه اسکریپت Python.
2. **حالت Bridge/Client:** Pico مادر فریم‌های معتبر را عبور می‌دهد؛ Pico کلاینت رویدادهای کیبورد را با مسیر HID فعلی اجرا و رویدادهای موس را به مسیر فعلی ARM/Pro Micro می‌فرستد.
3. **برنامهٔ بومی Windows:** فقط پس از پایدارشدن لینک، دریافت رویدادهای موس/کیبورد و ارسال آن‌ها از COM؛ یک کلاینت برای MVP.
4. اندازه‌گیری تأخیر و نوسان از ابتدا تا انتهای مسیر و اصلاح صف/فریم‌بندی بر پایهٔ اندازه‌گیری واقعی.

## الزامات رفتاری

- پخش با فرمان روشن و وضعیت آشکار شروع شود؛ رویدادها خارج از پخش ذخیره نشوند.
- قطع COM، قطع لینک یا توقف پخش باید ورودی‌های نگه‌داشته‌شدهٔ کلاینت را رها کند.
- فریم‌ها باید طول و شمارهٔ توالی داشته باشند و خطا/تکرار را تشخیص دهند. جزئیات رمزنگاری و مدیریت کلید پیش از انتقال رویدادهای HID نهایی می‌شود؛ از روی اتصال سریال به‌تنهایی رمزنگاری فرض نمی‌شود.
- تا وقتی آزمون یک کلاینت انجام نشده، چندکلاینتی به نسخهٔ اول اضافه نشود.

## وضعیت

- مخزن جداگانه ساخته شده تا این کار با ارتقاهای جاری برنامه مخلوط نشود.
- مسیر native UF2 از سورس فعلی بررسی شده؛ فایل‌های نمونهٔ قدیمی فقط مرجع‌اند و به مخزن اضافه نشده‌اند.
- هیچ بردی هنوز با فریمور جدید فلش یا روی سخت‌افزار آزمایش نشده است.
